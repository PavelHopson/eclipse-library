# Library Editor API

Отдельный сервис редактора Library. По умолчанию используется отдельный аккаунт Library. Опционально редактор может явно связать его с аккаунтом Eclipse Chat. Статический каталог напрямую не изменяется.

## Запуск

```bash
psql "$DATABASE_URL" -f schema.sql
npm ci --omit=dev
DATABASE_URL=postgres://... EDITOR_EMAIL=editor@example.com EDITOR_PASSWORD='set-a-long-password-here' ALLOWED_ORIGIN=https://library.eclipse-forge.ru node server.mjs
```

`EDITOR_PASSWORD` не кладётся в репозиторий. Для продакшена сервис работает за HTTPS reverse proxy на отдельном API-домене.

## Контракт

- `POST /api/editor/login`, `POST /api/editor/logout`, `GET /api/editor/me`;
- `GET/POST /api/editor/prompts`, `PATCH/DELETE /api/editor/prompts/:id`;
- `GET /api/editor/events` — SSE для realtime-обновлений.
- `POST /api/editor/prompts/:id/image` — загрузить PNG/JPG/WebP/GIF до 6 МБ как пример изображения.
- `DELETE /api/editor/prompts/:id/image` — удалить только пример изображения.

## Выпуск панели редактирования

Перед обновлением API применить актуальную `schema.sql` к базе Library: добавлена необязательная колонка `style_code` с пустым значением по умолчанию. Старые примеры сохраняются без привязки. Затем обновить API, после него статические страницы. При откате frontend/API колонку можно оставить — удаление данных не требуется.

`PATCH /api/editor/prompts/:id` принимает `expectedUpdatedAt` из последнего чтения карточки. Версия проверяется атомарно вместе с UPDATE; устаревшее сохранение возвращает 409 `edit_conflict`. Старые клиенты без поля сохраняют прежний контракт. `style_code` может быть пустым или slash-кодом до 60 символов; публичная страница показывает ссылку только для известного кода своего каталога.


## Общий вход Eclipse — кандидат, не включён на production

Владелец редактора и данных остаётся Library. Chat подтверждает личность, но не выдаёт права Library. Широкий общий токен, общая база аккаунтов или общий доменный cookie не используются.

Порядок включения после согласованной публикации:

1. На Chat сохранить действующий DnD-клиент и добавить серверную настройку `ECOSYSTEM_IDENTITY_CLIENTS_JSON`:
   `[{"id":"eclipse-library","sessions":true,"redirectUris":["https://library.eclipse-forge.ru/editor-api/api/editor/identity/callback"]}]`.
   Список клиентов разрешается только из доверенной конфигурации. Audience автоматически равен id клиента. Не менять DnD redirect для подключения Library.
2. Применить `schema.sql` в базе Library до обновления API. Добавляются `editor_identity_links` и nullable `editor_sessions.identity_link_id`. Существующие аккаунты, сессии и материалы сохраняются.
3. Установить `LIBRARY_CHAT_LOGIN_ENABLED=true`, `LIBRARY_CHAT_ISSUER=https://app.star-crm.ru/eclipse-chat` и точный `ALLOWED_ORIGIN=https://library.eclipse-forge.ru`. Без флага кнопка входа скрыта, endpoints выключены. Issuer должен быть доверенным HTTPS-адресом; JWKS и token endpoint выводятся из него, а не из пользовательского ввода.
4. Войти привычным паролем Library, раскрыть «Общий аккаунт Eclipse», нажать «Подключить мой аккаунт Chat», подтвердить свой аккаунт на странице Chat. Текущая парольная сессия повторно проверяется при возврате. Совпадение email не создаёт привязку. Уже занятые или отозванные привязки не переписываются.
5. Выйти из Library, войти через Chat, сохранить тестовый пример и проверить публичную страницу. Удалить только тестовый пример после проверки.

Все изменяющие запросы `/api/editor/*` требуют точный `Origin`, включая старый парольный вход и logout. Редактор отправляет его штатно; ручные API-клиенты должны указать его явно. Ответ CORS сам по себе не является авторизацией.

SSO-сессия Library действует до 8 часов, но не дольше связанной сессии Chat. При каждом редакторском запросе Library проверяет её на сервере Chat; SSE — каждые 15 секунд. Обновление refresh-токена Chat сохраняет идентификатор сессии и не прерывает Library. После 8 часов требуется повторный вход через Chat. Парольный вход Library сохраняет семь дней.

«Выйти из Library» завершает только текущую Library-сессию. «Выйти из Eclipse» с отдельным подтверждением удаляет связанную сессию Chat и отзывает все её серверные grants; другие устройства и парольные сессии Library остаются рабочими. Уже начатый запрос может завершиться, следующий запрос будет отклонён. При недоступности Chat API возвращает 503, не разрешает операции и сохраняет сессию для повторной проверки. Неудачный выход не очищает черновик.

Перед включением обязательны миграция Chat `20261107120000_ecosystem_sessions`, `AUTH_PROTOCOL_V2_REQUIRED=true` и проверенная совместимость установленных приложений Chat с протоколом v2. Без этого Chat отказывает в выдаче длинной сессии. Нельзя включать флаг вслепую ради Library.

В Library требуется отдельный `LIBRARY_IDENTITY_STORAGE_KEY_B64`: случайный 32-байтовый ключ в base64 из серверного хранилища секретов. Он шифрует grants через AES-256-GCM с привязкой к строке сессии. Chat хранит только SHA-256 grant; браузер получает только обычную HttpOnly cookie Library. При замене ключа существующие SSO-сессии потребуют нового входа. Ключ нельзя хранить в Git, логах или рядом с выгрузкой БД.

Для экстренного отзыва конкретной привязки владелец БД может установить `revoked_at=now()` по её проверенному id параметризованным запросом. API перечитывает права при каждом обращении; SSE перепроверяет сессию каждые 15 секунд. Механизма управления правами всех проектов через UI пока нет.

Откат: выключить `LIBRARY_CHAT_LOGIN_ENABLED` и оставить парольный вход. Текущий API сразу перестаёт принимать SSO-сессии. Перед возвратом на предыдущую реализацию удалить только строки `editor_sessions` с `identity_link_id is not null`, чтобы старый API не принимал длинные сессии без проверки Chat. Аддитивные таблицы/колонки оставить, парольные сессии и материалы не удалять.

## Проверка общего входа

- `node --test test/auth.test.mjs test/identity.test.mjs` — cookie, PKCE/state, подпись, issuer/audience, replay и конфигурация.
- `test/identity-integration.test.mjs` запускает реальный Library API и PostgreSQL; настоящие маршруты Chat обслуживаются через локальный HTTPS и Prisma из `apps/server/tests/helpers/ecosystem-session-fixture.ts`.
- Для интеграции требуются `LIBRARY_IDENTITY_TEST_DATABASE_URL` (только 127.0.0.1, база `library_identity_qa`) , `DATABASE_URL` (127.0.0.1, `chat_identity_qa`), `CHAT_IDENTITY_TEST_MODULE` (сборка fixture через esbuild: `--bundle --platform=node --format=esm --packages=external` внутри checkout Chat), `IDENTITY_TEST_CERT`, `IDENTITY_TEST_KEY` и `NODE_EXTRA_CA_CERTS` (локальный сертификат с SAN localhost). TLS-проверка не отключается. Применить схему Chat к отдельной тестовой базе, затем запускать `node --test test/*.test.mjs`. Тест очищает только эту изолированную БД; никогда не передавать рабочую базу.
- Проверка UI выполнялась на 320/390/768/1440 px. API-состояния в visual QA моделируются; реальная авторизация/публикация проверяются отдельным интеграционным тестом.


## Панель и локальные права Library (локальный кандидат)

`/admin.html` показывает реальные количества примеров, поиск материалов, текстовую историю и переходы в проекты. Управление подключено только к Library. Статические гайды, курсы и каталоги этим выпуском не превращаются в CMS.

Настроенный `EDITOR_EMAIL` при старте становится защищённым владельцем. Он создаёт локальные аккаунты (пароль 16–128 символов), назначает editor/viewer или отключает доступ. Владелец не меняется через UI; создание других owner запрещено. Editor редактирует/публикует примеры, viewer читает панель/примеры/историю. Chat подтверждает личность, роли остаются в Library. Смена роли и отзыв всех Library-сессий пользователя выполняются одним SQL-запросом. Отключение не удаляет его аккаунт или авторство.

Схему применить до нового API: расширение CHECK ролей, таблица истории и триггер. Текущее состояние примеров фиксируется однократно при миграции; каждое следующее INSERT/UPDATE записывает текстовую версию в той же транзакции. Файлы и внутренние пути в историю не копируются. Восстановление требует свежую expectedUpdatedAt и сохраняет изображение и текущий статус публикации. Удалённый пример не восстанавливается этим экраном. Последние 50 версий доступны в истории, старые записи не удаляются автоматически.

Порядок согласованного выпуска: резервная копия БД → schema.sql транзакционно → API → web → проверка владельца/редактора/просмотра. До публикации production продолжает прежнюю реализацию. Откат требует вернуть bootstrap-владельцу роль editor и завершить новые сессии перед старым API; расширенную схему/историю сохранить. На старый API нельзя откатывать без проверки остальных ролей.

Проверки на отдельной БД (никогда не использовать production):
- `LIBRARY_ADMIN_TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:55441/library_admin_qa node --test test/admin-integration.test.mjs test/auth.test.mjs test/identity.test.mjs` из editor-api. Тест очищает только явно проверенную локальную library_admin_qa.
- Затем `node scripts/library-admin-qa.cjs` из корня: настоящий API + Chromium, 320/390/768/1440, создание и смена доступа, просмотр/восстановление версии, запреты viewer, ошибка/повтор. Использует существующий `.artifacts/visual-qa/tools/node_modules/playwright`; отчёт и скриншоты в `.artifacts/admin-qa/`.

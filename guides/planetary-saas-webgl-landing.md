# Планетарный SaaS‑лендинг: WebGL‑глобус как карта продукта

> Практический blueprint страницы с фиксированной планетой, scroll‑камерой, маркерами и стеклянными секциями — без зависимости продукта от 3D.

Дата адаптации: **23.08.2026**
Источник идеи: пользовательский PDF `Earth.pdf`.
Статус: **адаптировано; внешняя GLB‑модель и текстуры исходника исключены**.

## Короткий вывод

Планета полезна, когда продукт действительно связан с географией: распределённая инфраструктура,
логистика, международные команды, глобальные события или покрытие сети. Если связь только декоративная,
глобус быстро превращается в тяжёлый шаблонный фон.

В хорошем варианте маркеры отражают реальные данные, DOM‑секции остаются читаемыми без canvas, камера
следует смыслу скролла, а мобильный режим получает упрощённый poster или лёгкую сферу.

## Модуль 1. Смысл и информационная архитектура

### Урок 1. Четыре секции

1. Hero: одно обещание и один измеримый результат.
2. Возможности: не более 3–4 рабочих сценариев.
3. Доказательства: реальные метрики, карта или кейс.
4. CTA/footer: следующий шаг, условия и контакты.

Планета меняет ракурс вместе с разделами: крупный общий вид → регион функции → глобальное покрытие →
спокойное финальное положение. Если ракурс нельзя связать с текстом, движение следует убрать.

### Урок 2. Маркеры — данные, а не декор

```ts
type GeoMarker = {
  id: string;
  lat: number;
  lon: number;
  label: string;
  status: "active" | "planned" | "incident";
  updatedAt: string;
  source?: string;
};
```

Пользователь может открыть список тех же точек без 3D. Цвет не является единственным носителем статуса.
Нельзя показывать фиктивное «глобальное покрытие» как работающую сеть.

## Модуль 2. Ассеты планеты

### Урок 1. Собственная модель или процедурная сфера

Самый безопасный старт — сфера с собственной/лицензированной day texture, отдельными night lights и
нормальной картой. GLB нужен только если у него есть реальная геометрическая ценность. Для каждой карты
зафиксируйте источник и лицензию; политические границы и названия требуют отдельной актуализации.

Сторонние `planet.glb`, cloud и light textures из исходного PDF не являются автоматически разрешёнными для
распространения.

### Урок 2. Day/night shader

Основа — dot(normal, sunDirection): освещённая сторона получает day texture, тёмная — night lights. Добавьте
небольшой Fresnel‑rim для атмосферы и отдельную прозрачную оболочку облаков. Не требуется несколько тяжёлых
composer pipelines, если визуальная разница мала.

## Модуль 3. Scroll‑камера

### Урок 1. Ключевые кадры вместо рассыпанных чисел

```ts
const cameraTrack = [
  { at: 0.00, position: [0, 0.2, 3.2], target: [0, 0, 0] },
  { at: 0.35, position: [-1.4, 0.3, 3.8], target: [0, 0, 0] },
  { at: 0.70, position: [1.2, -0.1, 4.5], target: [0, 0, 0] },
  { at: 1.00, position: [0.7, 0.2, 5.2], target: [0, 0, 0] }
];
```

Один progress интерполирует camera, planet rotation и DOM reveal. Уберите параллельные scroll‑listeners и
несогласованные timelines.

### Урок 2. Управление пользователем

OrbitControls допустимы только в явной зоне «Исследовать карту» и отключены во время обычной прокрутки.
Иначе пользователь случайно вращает мир вместо страницы. На мобильном карта открывается отдельным
действием, а основной скролл остаётся предсказуемым.

## Модуль 4. Производительность

### Урок 1. Профили качества

- **full:** sphere, day/night, одна cloud shell, markers, лёгкий bloom;
- **balanced:** меньше texture, без bloom и части динамических motes;
- **mobile:** low‑poly sphere, одна сжатая texture, ограниченные markers;
- **static:** responsive AVIF/WebP poster и HTML‑список.

Учитывайте compressed texture support, максимальный texture size и память, а не только скорость GPU.

### Урок 2. Загрузка и очистка

Hero HTML и poster входят в initial payload. Модель и карты загружаются после первого meaningful paint или
по приближению к сцене. DRACO decoder берётся из контролируемого origin или закреплённой версии. На уходе
со страницы освобождаются geometry, material, textures, render targets, controls и listeners.

## Модуль 5. Стеклянные панели без шаблонности

### Урок 1. Контентная иерархия

Стекло используется только для отделения текста от движущегося фона. Не делайте все элементы полупрозрачными:
важная кнопка, таблица и юридический текст требуют стабильной поверхности и контраста.

### Урок 2. Состояния

Карточки возможностей имеют hover только как дополнение. На keyboard focus видно действие; на touch нет
скрытого обязательного контента. Loading/empty/error для карты и данных проектируются отдельно от WebGL.

## Модуль 6. Контракт для coding‑агента

### Урок 1. Адаптированный запрос

```text
Создай SaaS‑лендинг, где fixed WebGL‑планета объясняет реальное глобальное
свойство продукта. HTML‑контент и CTA должны быть полноценными без canvas.

Используй только наши лицензированные planet/cloud textures или procedural sphere.
Маркеры приходят из типизированных данных и дублируются доступным списком.
Scroll управляет одной cameraTrack; OrbitControls включаются только в отдельном
explore режиме.

Добавь full/balanced/mobile/static profiles, poster-first loading, reduced motion,
save-data, DPR/FPS budgets, pause on hidden, context-loss fallback, disposal,
desktop/mobile visual QA и проверку контраста на разных ракурсах.
```

### Урок 2. Приёмка

- смысл продукта понятен без глобуса;
- все маркеры имеют источник или явно помечены demo;
- scroll и touch не конфликтуют с OrbitControls;
- mobile грузит облегчённый asset, а не desktop GLB;
- reduced motion убирает camera fly‑through;
- отказ texture/decoder показывает poster;
- при повторных переходах не растут GPU memory и listeners.

## Модуль 7. Применение в Eclipse

### Урок 1. Реальные сценарии

- **Eclipse AI Office** — карта распределённых runtime‑узлов и агентов, только как view над Event Bus;
- **Eclipse Forge Landing** — отдельный кейс глобальной инфраструктуры;
- **StarMarket** — карта доступности/логистики, если данные действительно существуют;
- **Eclipse Library** — reusable geo marker contract и quality profiles.

### Урок 2. Критическое правило

3D‑планета никогда не является источником состояния. Состояние живёт в API/Event Bus, а сцена только
визуализирует его. При падении WebGL таблица, статусы и действия продолжают работать.
